# 首爾共享單車租借量預測：研究規劃與實驗說明

版本：2026-10-20。對象：預測學習課程四人小組。

本文件是期中研究提案與期末實作規格。已完成教材與論文閱讀、公開資料來源查核、UCI 原始 CSV 的結構檢查；尚未訓練模型，沒有本組實驗結果。文中模型排名、特徵貢獻與誤差型態均屬待驗證問題。投影片暫不製作。

## 1. 建議研究主軸

**中文題目：天氣資訊可得性與模型複雜度對首爾共享單車租借量預測的影響**

**英文題目：Weather Information Availability and Model Complexity in Seoul Bike Rental Forecasting**

研究目的：在一致的時間外評估流程中，檢驗歷史天氣能否改善下一小時租借量預測，量化使用目標小時實際天氣的事後優勢，並分析正則化、模型複雜度與歷史租借特徵如何影響泛化。

你們的兩套編號應分開：

- **E1、E2、E3 是資訊情境**：無天氣、歷史天氣、Oracle 天氣。
- **X1～X5 是分析實驗**：模型比較、正則化、複雜度控制、特徵消融、時間誤差分析。

這樣五項實驗具有共同研究問題，而不是五份獨立的模型練習。主分析以 E2 為實際資訊可得性的近似情境，E1 為資訊對照，E3 為事後診斷。

### 研究問題與假說

| 編號 | 研究問題 | 待驗證假說 | 對應實驗 |
|---|---|---|---|
| RQ1 | 使用最近已觀測天氣，是否比完全不用天氣更準？使用目標小時實際天氣，結果又差多少？ | E2 可能優於 E1；E3 可能改善部分降水時段，但不保證整體較好 | X1、X4、X5 |
| RQ2 | 在固定特徵下，哪種模型與複雜度能較好預測較晚月份？ | 適度正則化可能改善泛化；複雜模型未必勝出 | X1、X2、X3 |
| RQ3 | 模型主要依靠時間週期、日曆、歷史需求還是天氣？錯誤集中在哪些時段？ | 歷史需求可能提供較大增益；尖峰可能有較大絕對誤差 | X4、X5 |

這些假說不是結論。天氣沒有增益、Ridge 優於 RF、LSTM 沒有優勢，都是可以解釋的研究結果。

## 3. 預測任務與時間索引

### 3.1 目標是租借次數

預測全系統下一小時的 `Rented Bike Count`，單位是每小時租借次數。不能從此資料推論不重複使用者人數，也不能把已實現租借量完全等同於包含缺車未成交部分的潛在需求。

資料沒有站點、還車流量與庫存，因此本專題不直接解決站點調度或缺車率。

### 3.2 全組統一用目標時間 τ 定義欄位

把時間戳記 τ 的 y_τ 解釋為該小時區間的租借次數，例如 τ=09:00 代表 09:00～10:00 的租借量。

在 09:00 做預測時，假設 08:00～09:00 已完成彙整：

| 名稱 | 一般式 | 預測今天 09:00～10:00 時的意義 |
|---|---|---|
| target | y_τ | 今天 09:00～10:00 |
| lag_1 | y_(τ−1h) | 今天 08:00～09:00 |
| lag_24 | y_(τ−24h) | 昨天 09:00～10:00 |
| lag_168 | y_(τ−168h) | 上週同一天 09:00～10:00 |
| E2 weather | W_(τ−1h) | 最近完成小時 08:00～09:00 的天氣 |
| E3 weather | W_τ | 未來目標區間 09:00～10:00 的實際天氣 |
| Hour、Weekday、Seasons、Holiday | calendar_τ | 目標小時的時間／日曆資訊 |

若沿用你們圖片的「預測 y_(t+1)」，就令 τ=t+1。此時 lag_1=y_t、lag_24=y_(t−23)、lag_168=y_(t−167)。以目標列使用 shift(1)、shift(24)、shift(168)，能避免 off-by-one 錯誤。

E2 的操作可行性假設是需求與氣象資料在上一小時結束後立即可用。資料集不提供發布延遲，不能證明現實服務一定零延遲。若未來有實際延遲，需再使用較舊的觀測。

### 3.3 一小時滾動預測

每小時取得最新已觀測資料，重新形成輸入，但主實驗不在測試期間重新訓練模型。測試期較早小時的實際 y 可以在較晚預測時進入 lag，因為到那時已觀測到。

這不是在 7 月 1 日一次預測未來五個月。若要做後者，就不能使用測試期間新發生的實際租借量作為輸入。

## 4. E1／E2／E3 與特徵字典

| 情境 | 共用特徵 | 天氣特徵 | 研究定位 |
|---|---|---|---|
| E1 No Weather | 時間、季節、假日、三個歷史需求 lag | 無 | 無顯式天氣輸入的基準 |
| E2 Historical Weather | 同 E1 | W_(τ−1h) | 主情境，假設最近觀測已可取得 |
| E3 Oracle Weather | 同 E1 | W_τ | 事後資訊對照，不能部署 |

E3 **替換** E2 的五個天氣欄位，不把兩組一起放入。這樣 E2 與 E3 維持相同欄位數，較容易解釋資訊時點的差異。

E1 仍包含 Seasons 與歷史租借量，所以不是「完全沒有氣候訊息」，而是沒有顯式天氣觀測欄位。

### 特徵與前處理

| 群組 | 原始／衍生欄位 | 前處理 | 輸出維度 |
|---|---|---|---:|
| H：歷史需求 | lag_1、lag_24、lag_168 | 每欄 StandardScaler | 3 |
| T：時間週期 | 目標 Hour、Weekday | 各自 sin/cos 編碼 | 4 |
| C：日曆 | 目標 Seasons、Holiday | One-hot，全四季及兩種假日類別 | 6 |
| W：天氣 | Temperature、Humidity、Wind speed、Rainfall、Snowfall | 每欄 StandardScaler | 5 |

在上述不刪 dummy 欄位的規格下，E1=13 維，E2/E3=18 維。Weekday 規定 Monday=0、Sunday=6。Wind speed、Rainfall、Snowfall 要按原始 CSV 的欄名、單位正確對應。

時間週期公式：

```text
hour_sin = sin(2π × Hour / 24)
hour_cos = cos(2π × Hour / 24)
weekday_sin = sin(2π × Weekday / 7)
weekday_cos = cos(2π × Weekday / 7)
```

sin 與 cos 必須成對保留，例如只用 sin 無法完整區分一天中的位置。

數值標準化：

```text
z = (x − 訓練集平均數) / 訓練集標準差
```

每個模型情境與消融版本，在自己的訓練資料上 fit preprocessing；validation/test 只 transform。E2 與 E3 的 weather scaler 分別由其訓練欄位估計。sin/cos 與 one-hot 不再標準化。

樹模型通常不需要 StandardScaler，但可為了統一資料流程沿用相同轉換。不要把樹模型的效果歸因於標準化。對 Ridge、KNN，尺度尤其重要。

### 保留你們的選擇

核心實驗不額外加入 Visibility、Dew point temperature、Solar Radiation、Month、移動平均或其他外部資料。這些可以成為之後的新增特徵實驗，但要獨立編號，不能悄悄更改 E1～E3。

降雨／降雪的 0 是有效觀測，不是 missing value。主分析不對 rainfall/snowfall 任意取 log、不刪除需求高峰、不全資料去極端值。若真的需要離群處理，規則只能從訓練資料決定，並保留原始版本對照。

季節四分類的詞彙是預先已知的日曆定義，可先固定，不需要查看測試分布才能決定。訓練期沒出現的季節仍沒有可學習的係數／分裂規則；固定類別只避免程式失敗，無法創造該季節的經驗。

## 5. Master Dataset 的正確建立方式

「統一資料」應指統一時間戳、目標、特徵來源與樣本集合，**不是先把全部資料標準化再切分**。

建議順序：

1. 保存原始 CSV、來源 URL、取得日期、SHA-256。
2. 以日／月／年解析 Date，再加上 Hour，形成每小時唯一時間戳。
3. 排序並檢查重複、缺時、欄位型態及缺失。
4. 在完整每小時時間軸建立需求 lag，以及歷史／目標小時天氣欄。
5. 建立目標時間的 cyclical 與 calendar 原始欄位。
6. 建立三情境共用的 eligible mask。
7. 依目標時間切成 train／validation／test。
8. 在各 train 子集中 fit scaler／encoder，再 transform 對應 validation/test。
9. 從 Master Dataset 明確選出 E1、E2、E3 欄位清單。

Master Dataset 可以存兩組天氣，但模型只能透過白名單取欄位，禁止直接使用「全部數值欄」。`target`、Functioning Day、split、eligible、timestamp 都屬標籤或管理欄，不能自動混入 X。

### 為什麼先建立 lag 才篩選營運小時？

停駛小時也是時間軸的一部分。如果先刪除停駛列，shift(24) 會變成「24 筆營運紀錄之前」，不一定是 24 小時前。

主規格：

- 在完整時間軸保留停駛小時及其觀測租借數，建立 lag。
- 只把目標小時 `Functioning Day == Yes` 的列列入訓練與評分。
- 三個 lag 都存在後才納入樣本，前 168 小時作為暖機資料。
- 歷史停駛的 0 可以進入 lag，因為是當時已觀測的實現租借量。它不等於當時潛在需求為 0。
- 此評估是「條件於實際營運小時」的預測評估。資料未證明預測時已知道未來停駛，因此不能宣稱整個停駛判斷流程已可部署。

可加一個敏感度檢查：排除三個 lag 所對應小時曾停駛的目標列，對照結果是否受停駛的 0 影響。這是次要分析，不能與主實驗混成同一樣本集。

## 6. 統一的時間切分與模型選擇

### 主評估

採用原論文的日期邊界，但使用本組的特徵、168 小時暖機與樣本定義：

| 集合 | 目標時間 | 角色 | 預計有效樣本 |
|---|---|---|---:|
| Train | 2017-12-08 00:00 至 2018-05-31 23:00 | 估計前處理參數與模型參數 | 4,152 |
| Validation | 2018-06-01 至 2018-06-30 | 選超參數、early stopping | 720 |
| Test | 2018-07-01 至 2018-11-30 | 最終評估與預先指定的分組分析 | 3,425 |

日期為資料本身的首爾當地小時，不需要換成執行電腦時區。筆數來自 UCI CSV，若資料來源或篩選規則改變須重算。

主規格**不在挑完參數後合併 train+validation 重訓**，讓訓練期、曲線與最終模型一致，也避免 LSTM 重訓時 early stopping 定義不清。驗證集用於選擇，但不作梯度／係數估計。所有模型遵守同一規則。

因此訓練資料是冬春、驗證是夏季、測試是夏秋。模型選擇已接觸夏季驗證表現，不能宣稱夏季完全未被開發流程看見。時間、季節與可能的需求成長混在一起，也不能由這一切分單獨證明季節造成誤差變化。

### 防止選模污染

- 不隨機切分、不使用 shuffled K-fold 作為主驗證。
- 所有候選模型都用同一個 validation MAE 選參。
- 先固定比較、消融和分組清單，再開始最終 test 評估。
- test 可一次產生所有預先登記的結果，不等於只能評估一個模型；但不能看完 test 再增加候選、挑選特徵或決定主模型。
- test 開發前的結構、日期與筆數核對不等於用 test 誤差選模；主 EDA 圖形以 train 為主。
- 如果後來依 test 發現新假說，標為探索性分析，不能冒充未見資料驗證。

### 時間穩健性，期末次要分析

若工時允許，在最終 test 之前加入兩個 expanding-window 檢查：

1. 訓練至 2018-02-28，驗證 2018-03。
2. 訓練至 2018-04-30，驗證 2018-05。

仍以六月 validation 決定主規格，前述月份用來看排名與 alpha/k 的敏感度。每折重新 fit preprocessing，按日期切分。因為篩過停駛目標後索引不再等距，不要把固定「筆數」的 TimeSeriesSplit 誤當成固定月長。

單步預測且所有特徵嚴格向過去取值時，跨邊界讀取之前已觀測的 lag 是合法的，不需機械式刪掉每段開頭 168 小時。若未來改成多步預測、重疊標籤或延遲發布，才須重新設計 gap／embargo。

## 7. 模型範圍與 LSTM 公平性

### 核心：固定你們選好的特徵

| 模型 | 角色 | 主要可控制項 |
|---|---|---|
| Persistence | 前一小時基準：ŷ_τ=lag_1 | 無 |
| Daily seasonal naive | 前一天同小時：ŷ_τ=lag_24 | 無 |
| Weekly seasonal naive | 上週同小時：ŷ_τ=lag_168 | 無 |
| Ridge | 線性、L2 正則化 | alpha |
| KNN regressor | 局部非線性模型 | k |
| Random Forest regressor | 樹集成非線性模型 | max_depth、min_samples_leaf |
| Decision Tree | X3 複雜度教學對照 | max_depth |

三個 naive 的預測不隨 E1／E2／E3 改變，結果表不用重複訓練它們。必須知道機器學習是否勝過昨天同時段等簡單預測，而不只比較模型彼此。

### LSTM 保留為期末的匹配資訊延伸

你們選的 lag_1、lag_24、lag_168 是三個不等間隔觀測，**不能直接宣稱它們是一段連續 24 小時序列**。把所有異質特徵 reshape 成 time steps，也不會自動變成合理的時間模型。

建議保留 LSTM，但另外建立「序列延伸軌」，避免改壞已選好的核心特徵：

- 共同新增 lag_1～lag_24，保留 lag_168。
- LSTM 按從舊到新的順序讀取 24 個需求值，最後隱藏狀態再接上 lag_168、目標時間／日曆、E1/E2/E3 的天氣。
- Ridge、KNN、RF 也取得相同的 24 個需求 lag 與 lag_168，展平成表格輸入。
- 不額外給 LSTM 24 小時天氣序列，除非其他模型也取得相同資訊。
- lag_168 仍決定共同暖機期，因此樣本集合可以和核心軌一致。
- 延伸軌內才能比較「相同原始資訊下，LSTM 是否值得」。

如此保留原先的 LSTM 目標，同時避免把「多拿到歷史資料」誤解為「架構比較好」。核心軌與延伸軌分表報告。如果期末時間不足，先完成全部五項核心分析，再完成 LSTM 延伸；期中把這個優先順序講清楚。

LSTM 初始範圍：單層、hidden_size∈{16,32}、dropout=0、Adam learning_rate=0.001、batch_size=64、max_epochs=100、patience=10。以反標準化後 validation MAE 選 checkpoint。需求輸入與 target 的 scaler 只從訓練範圍 fit，target 不使用 log1p 作為主設定，維持原尺度 MSE 的學習目標。

先用 seed=42 做小網格，固定設定後以 42、43、44 三個 seed 報告平均與標準差。不要選 test 最好的 seed。LSTM 結果限於所測的小型架構與預算，不推論整個深度學習家族。

## 8. 五項實驗的完整規格

### X1. Baseline Comparison：資訊情境與模型比較

**問題：哪個模型在較晚月份誤差較低？天氣資訊時點是否改變排名？**

核心矩陣是 3 個模型 × 3 個資訊情境，共 9 組選模流程，另加三個 naive。LSTM 延伸另列。

初始候選：

| 模型 | 事前固定搜尋範圍 |
|---|---|
| Ridge | alpha∈{10⁻⁴,10⁻³,…,10⁵}，共 10 個 |
| KNN | k∈{1,3,5,9,15,25,49,97}，uniform weights，Euclidean distance |
| RF | n_estimators=200，max_depth∈{4,8,16,None}，min_samples_leaf∈{1,5,20}，max_features=1.0，bootstrap=True，seed=42 |

每個情境各自以 validation MAE 選最佳參數，回答「同一模型家族在不同資訊條件下，能取得什麼表現」。另由 X4 固定超參數的對照，幫助分辨資訊與調參的影響。

若最佳參數落在網格邊界，可在查看 test 前依事前規則向外延伸一次，並同步記錄。完成後鎖定網格；不要依 test 結果加大搜尋。

最終表格欄位：

```text
track, scenario, model, selected_params, seed,
n_train, n_val, n_test, validation_MAE, test_MAE, test_RMSE,
fit_seconds, predict_seconds, hardware
```

主模型以 **E2 validation MAE** 選定。test 排名是最後評估結果，不能倒過來改寫選模決策。

### X2. Regularization：Ridge 的 alpha

**問題：L2 懲罰如何改變擬合與時間外誤差？**

主圖固定 E2，使用與 X1 同樣的 alpha 網格。E1／E3 曲線可作補充，不把全部模型套上 alpha。

scikit-learn Ridge 的目標為：

```text
min_(w,b) Σ_i (y_i − b − x_iᵀw)² + alpha × ||w||²
```

截距不受 L2 懲罰。若用課堂的「平均平方誤差 + λ||w||²」表示，對相同 n 有 alpha=nλ，兩個數值不要直接混用。

每個 alpha 保存：

- 訓練及驗證 MAE、RMSE。
- 未截斷預測的訓練 MSE，方便解釋擬合代價。
- 標準化特徵下的係數 L2 norm。

橫軸為 log10(alpha)，主曲線畫 train／validation RMSE，另標以 validation MAE 選出的 alpha。不要在選參圖上同時畫 test 再選最低點。

預期過弱懲罰可能過擬合、過強可能欠擬合，但真實曲線未必呈漂亮 U 形。不可事先畫一條理想 U 形當成實驗結果。不同 alpha 的 penalized objective 不是同一個評估量，也不能直接用其大小比較泛化。

### X3. Complexity Control：KNN 與樹深度

**問題：增加模型彈性，是否只降低訓練誤差，卻沒有改善驗證？**

兩個清楚的控制實驗都固定 E2：

1. KNN 使用同一組 k。k 小代表更局部、通常更靈活；k 大平均更多鄰居，通常更平滑。橫軸若畫 k 由小到大，複雜度方向通常由高到低。
2. 單棵 Decision Tree 使用 max_depth∈{2,3,4,6,8,12,16,None}，其他參數固定，seed=42。作為深度控制的清楚對照，不混入 RF 的 bagging 效果。

畫 train／validation RMSE，保存 MAE、實際 leaf count。RF 的深度敏感度可補充，n_estimators 固定 200，不同時改深度、葉節點大小及樹數，避免失去控制變因。

KNN k=1 在訓練資料上自我查詢會得到接近零誤差，這是 resubstitution 的結果，不是有效預測能力的證據。

觀察到較大的 train／validation 差距，可以討論泛化問題，但不能由一條曲線直接估出統計上的 bias 和 variance；時間分布改變也可能造成落差。

### X4. Feature Ablation：資訊群組的增量價值

**問題：在其他資訊存在時，拿掉哪一組會讓表現改變？**

以 Ridge 與 RF 兩種模型先做消融，避免四人組的計算量失控。

第一部分比較三種天氣資訊：

```text
E1 = H + T + C
E2 = H + T + C + W_(τ−1h)
E3 = H + T + C + W_τ
```

第二部分在 E2 中做 leave-one-group-out：

| 版本 | 拿掉的欄位 | 用途 |
|---|---|---|
| Full E2 | 無 | 參考 |
| −H | lag_1、lag_24、lag_168 | 歷史租借量的增量價值 |
| −T | Hour/Weekday 的四個 sin/cos | 時間週期的增量價值 |
| −C | Seasons、Holiday one-hot | 日曆的增量價值 |
| −W | 五個歷史天氣欄 | 等同 E1 |

所有版本沿用 Full E2 的樣本集合，不能讓 −H 因為不需要暖機就多拿 168 小時。

主消融先固定 Full E2 在 validation 選出的超參數，只重新 fit 模型及其前處理。這回答「原設定拿掉資訊會如何」。次要敏感度分析可在各子集重新調參，但必須分表，說明它回答「子集在重新優化後能做到什麼」。

定義：

```text
ΔMAE_remove(G) = MAE(−G) − MAE(Full E2)
Gain_history = MAE(E1) − MAE(E2)
Gap_oracle = MAE(E2) − MAE(E3)
```

正的 ΔMAE_remove 表示拿掉 G 後誤差增加。正的 Gap_oracle 表示事後天氣在這個模型與設定下有優勢，不是天氣預報系統的實際效益，也不是保證可達的理論上界。

移除特徵不等同因果介入。氣溫與季節相關，需求 lag 也承載天氣及行為訊息，因此「−W 沒變差」不代表天氣不影響使用者。

### X5. Temporal Analysis：錯誤發生在哪裡？

**問題：平均 MAE 是否掩蓋某些時段、月份或天氣情境的問題？**

主要分析對象：事前由 validation 選出的最佳 E2 模型，搭配最好的 naive。天氣時點分析則對同一模型家族比較 E1/E2/E3。

在看 test 結果前固定分組：

| 分組 | 定義 |
|---|---|
| 夜間 | 目標 Hour=00～05 |
| 早尖峰 | 07～09 |
| 晚尖峰 | 17～19 |
| 其他 | 06、10～16、20～23 |
| 星期 | 週一至週五／週六日，另外標示 Holiday |
| 月份 | 7、8、9、10、11 月 |
| 降水 | 目標小時 Rainfall>0 或 Snowfall>0 |
| 無降水 | 目標小時 Rainfall=0 且 Snowfall=0 |

上述尖峰是事前操作定義，不宣稱已由 test 證明是實際最高峰。若分析「通勤尖峰」，再限制週一至週五且非 Holiday。

每組報 n、實際平均租借量、MAE、RMSE、平均有號誤差 mean(ŷ−y)。負值表示低估。降水分組使用目標小時天氣是事後評分標籤，不進入 E2 輸入。

至少做：

1. 0～23 小時各自 MAE。
2. 依月份的 MAE 與樣本數。
3. 同一模型 E1/E2/E3 在有／無降水時的 MAE。
4. 預先固定 2018-07-01～07-07 的 actual vs. predicted 曲線。

不可挑出模型表現最好的一週當唯一展示。若補充最差案例，明確標為事後錯誤診斷。降水不全部都是「極端天氣」，不要沿用原論文的 extreme 標籤卻省略其定義。

## 9. 指標、統計與結果解讀

主指標：

```text
MAE = mean(|y − ŷ|)
RMSE = sqrt(mean((y − ŷ)²))
```

兩者以原始租借次數／小時報告。MAE 易於解釋，RMSE 對大誤差更敏感。所有模型以 max(0, ŷ) 作為統一最終輸出，不四捨五入為整數；Ridge 訓練擬合診斷另外保留未截斷預測。

不以 MAPE 當主指標，因為小租借量與零值會讓百分比誤差不穩定。若加相對改善：

```text
Relative MAE reduction = (MAE_reference − MAE_model) / MAE_reference
```

分母是哪個 baseline 必須寫清楚，分母為零時不計算。

E3 是更多事後資訊的一個特定表示：它替換 W_(τ−1h)，並非嚴格包含 E2 的所有欄位，加上有限樣本、模型限制與調參，所以不保證 E3 MAE≤E2 MAE。

### 隨機性與不確定性

- Ridge／固定 KNN 通常不需要重複 seed。
- RF 與 LSTM 在設定鎖定後用 seed 42、43、44，報平均及標準差。這反映演算法隨機性，不是跨年份泛化的不確定性。
- 如要比較模型誤差的區間，可做配對日曆區塊 bootstrap：先按日保存每模型 absolute-error sum、squared-error sum、有效 n，再按連續 7 天區塊共同重抽，重算 MAE 差異。兩模型必須抽相同日期。
- 缺營運小時的天仍保留日曆位置與 n，不能把不相鄰營運紀錄當連續時間。
- 以 1,000 次重抽作描述性 95% 區間，另以 1 天區塊做敏感度比較。時間相關及月份分布改變使此區間有局限，不能包裝成保證未來城市或年份表現的檢定。
- 多組實驗優先報效應量，不追求每個子群都出現「顯著」。

### 可能出現的結果如何解釋

| 現象 | 合理解釋方向 | 不能直接下的結論 |
|---|---|---|
| E2≈E1 | 需求 lag 與季節已有相關資訊；天氣 lag 太舊；模型沒抓到交互作用 | 天氣對租借沒有影響 |
| E3 明顯較好 | 目標小時天氣有額外預測資訊 | 真實天氣預報也能提升同樣幅度 |
| RF 優於 Ridge | 所選特徵下的非線性有用 | RF 永遠最好 |
| Ridge 優於 LSTM | 有限資料、輸入表示或訓練預算更適合簡單模型 | 深度學習沒有用 |
| 尖峰 MAE 較高 | 需求尺度較大或變動更劇烈 | 相對誤差必然也更高 |
| 訓練好、測試差 | 過擬合或時間分布變化，需再診斷 | 已證明是某一個因素造成 |

主要工具：Python、pandas、scikit-learn、matplotlib，以及延伸的 PyTorch 或 TensorFlow 擇一。核心模型可用一般電腦 CPU；LSTM GPU 為可選，先量測實際耗時再決定。現有電腦與免費軟體可完成核心，預算先以無額外支出規劃，未要求付費雲端資源。

UCI 資料頁標示 CC BY 4.0，正式報告需引用來源。論文若重製圖表另依該文授權與引用要求。

主要限制：

- 一個城市、一年資料，不能推廣為跨城市或多年定律。
- 時間變化與季節同時發生，不能作季節因果推論。
- 聚合租借量不等於站點需求或未滿足需求。

- 原始 one-hot 季節無法讓模型學會訓練期沒見過的季節效果。
- 核心是點預測，不回答區間覆蓋率及校準問題。

## 15. 預先準備的 QA

**Q：為何不直接重做 Transformer？**

A：我們的研究問題是資訊可得性與複雜度控制。簡單模型能提供較清楚的控制實驗，也能直接連結課堂內容。LSTM 以匹配資訊的延伸比較保留，模型複雜並非研究品質的必要條件。

**Q：E3 算不算資料洩漏？**

A：若把 E3 當成預測當下可用資訊，屬於前視問題。本研究明確把它列為事後 Oracle 對照，不把它的成績當成部署成績。E1/E2 是不使用目標小時實際天氣的對照。

**Q：為何 E2 還需要天氣，lag_1 不就反映天氣了？**

A：這正是研究問題。需求 lag 可能含部分天氣訊息，但不一定充分；比較 E1/E2 及分組消融可以量化額外預測價值。

**Q：為何不用隨機 train/test？**

A：任務是預測較晚時間。隨機切分容易讓訓練資料包含相近或更晚的時段，回答的泛化問題不同，因此主分析遵守時間順序。

**Q：為何測試時可以使用測試期之前的實際租借量？**

A：我們每小時滾動預測下一小時，較早的觀測在當下已經可取得；模型參數仍保持凍結。如果一次預測五個月，則不能這樣做。

**Q：為何不保證 E3 最好？**

A：E3 替換天氣欄位，資訊集合不是嚴格包含關係，而且有限資料與模型限制可能使新增資訊無法轉化為更低誤差。

**Q：訓練和測試差很多就代表過擬合嗎？**

A：可能是過擬合，也可能是需求與氣象分布變化。我們用複雜度曲線及月份／情境分析檢查，避免只靠一個誤差差距下結論。

**Q：這是原論文的重現嗎？**

A：屬於以原論文為起點的延伸課程研究。我們沿用資料背景與日期邊界，但核心特徵、模型及評估目的不同，不宣稱完整重現或直接優於原論文。

**Q：為何不給 LSTM 更多序列、其他模型用三個 lag？**

A：那會同時改變模型與資訊量。延伸軌會讓所有模型取得相同 24 小時需求與 weekly lag，才能較清楚比較架構。
